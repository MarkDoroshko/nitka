# Проверка обобщения на новых формах

Задача 8 проверяет применимость текущих правил к другим макетам. Набор состоит из девяти синтетических файлов, созданных отдельно от материалов настройки OCR. Для оценки на новых реальных документах потребуется независимая размеченная выборка. [Генератор](../examples/generalization_corpus.py) и [разметка](../examples/generalization_expected.json).

## Как повторить

Соберите образ с тегом `nitka:local`. Для оценки понадобятся проверенные веса PP-OCRv5. Оценка использует CPU OCR и работает без сети. [Инструкция Docker](../README.md#запуск-в-docker), [веса PP-OCRv5](../config/ocr/README.md).

Команды PowerShell запускаются из корня проекта.

```powershell
$repo = (Get-Location).Path
$models = (Resolve-Path 'models/ppocr-v5').Path
New-Item -ItemType Directory -Force runs | Out-Null
docker run --rm --network none `
  --mount "type=bind,source=$repo/examples,target=/app/examples,readonly" `
  --mount "type=bind,source=$repo/runs,target=/evaluation" `
  --mount "type=bind,source=$models,target=/models,readonly" `
  nitka:local python -m examples.run_generalization `
  --font /usr/share/fonts/truetype/dejavu/DejaVuSans.ttf `
  --models /models --output /evaluation/generalization
```

Укажите новый каталог при каждом запуске. При запуске вне Docker установите зависимости разработки, OCR и передайте пути к локальным моделям и шрифту DejaVu Sans. Отчёт `runs/generalization/report.json` содержит числители и знаменатели, суммы по полям, связи, статусы, причины блокировок и идентификаторы сохранённых запусков. Для каждого комплекта сценарий проверяет равенство результата после загрузки и повторного расчёта. JSON фиксирует версии, параметры OCR и SHA-256 входов, шрифта, эталона и кода. Отсутствие подтверждённого OCR на любой обязательной странице даёт `complete: false` и код выхода 2. Успешный прогон может зафиксировать отказ приложения обработать форму.

## Что измеряется

- **Денежные поля.** Численно точные значения без отметки ручной проверки делятся на все размеченные поля. В знаменателе остаются пропуски и неразобранные значения. Из первички считаются применяемые суммы, включая обе строки оплаты труда и начисленные взносы. Справочная база взносов и формульный итог ведомости вне метрики.
- **Связи.** Неверные связи делятся на все `ACCEPTED` пары «статья — документ». У каждого исходного документа одна операция. Повторные принятые операции одного документа учитываются в числителе, а принятые пары для заблокированных статей входят в знаменатель. Отдельно считаются пропущенные ожидаемые пары. При нуле принятых пар доля ошибок не определена.
- **Непроверенные строки.** В каждом комплекте проверяются 0200, 0300, 0800, 0900 и напечатанный общий итог по первичке. Статусы `PASS` и `FAIL` означают, что сверка выполнена. Отсутствие проверки, `NOT_RUN` или подстановка суммы статей вместо напечатанного итога оставляют строку непроверенной. Внутренняя арифметика КФЗ и детализация учитываются отдельно от этих пяти проверок.

## Измерения 14 ноября 2026 года

Прогон выполнен в Linux-контейнере без сети на коде `3c5e9213723b04634ee8a19ed4f8a1033edf02be`. Runtime включал PaddleOCR 3.7.0, PaddleX 3.7.2 и ONNX Runtime 1.31.1. OCR подтвердился на обеих ожидаемых страницах каждого комплекта. Первоначальный макет нумерованной КФЗ дал 9/14 денежных полей. После просмотра рендера развели два соприкасавшихся заголовка и уменьшили шрифт цифр для читаемости. Размеченные значения и правила приложения сохранились. Ниже приведён прогон финальных макетов.

Повторный прогон финальных макетов дал те же SHA-256 всех девяти входов и те же счётчики. Отпечаток кода конвейера в `sha256.pipeline` — `9d3cc4a1bdfad2d8874595dc64ba510475e28e5550fdd00b65974cd6902d0dd8`. Проверка трёх комплектов вместе с загрузкой и повторным расчётом заняла 33 секунды.

Одинаковые файлы в нескольких комплектах учитываются в каждом прогоне. Нумерованная КФЗ дала 14/14 размеченных полей. В вертикальной КФЗ строка не выделилась и проверка области заблокировала сопоставление. XLSX со сдвинутой таблицей дал 0/2 полей. Он заблокировал расчёт и в комплекте, где матчер успел принять четыре связи. Цифровые акты PDF, скан УПД PNG, таблица DOCX и расчёт взносов XLSX сохранили все пять размеченных сумм в каждом комплекте. Для скана остались замечания к номеру и договору.

В контроле подтвердились 0200, 0300 и 0900. По 0800 КФЗ показала 48 700,50 ₽, первичка подтвердила 48 600,50 ₽. Разница +100,00 ₽ повторилась в общем итоге. Акт на 48 700,50 ₽ по другому договору исключён по договору. Девять детализированных показателей КФЗ требуют ручной проверки и в контроле.

## Границы пилота и подключение новых форм

Пилот ограничен нумерованной КФЗ с проверяемыми заголовками и областью, известными формами XLSX и одиночными операциями первички с читаемыми реквизитами. Ревизор сверяет OCR-фрагменты, договор, период и статью, а также проверяет полноту комплекта перед выводом о завышении. Вертикальная КФЗ и сдвинутая ведомость направляются на ручной разбор. Результаты по одному скану и нескольким макетам достаточны для проверки этих сценариев, а допуск новых семейств требует реальных пакетов.

1. Собрать реальные обезличенные комплекты из нескольких источников. До настройки зафиксировать отдельную контрольную выборку по семействам документов, включая соседние строки, чужие договоры и неполную первичку.
2. Для вертикальной КФЗ определить явные признаки шаблона и правила выбора периода, этапа и строки. Для сдвинутой XLSX определить уникальные заголовки и проверку соответствия кодов суммам. При нескольких подходящих таблицах оставить ручную проверку.
3. Добавить разметку полей, связей, статусов и причин пропуска для каждого семейства. Повторить тот же протокол на отложенных документах и исходном кейсе. Перед допуском проверить каждую обнаруженную неверную связь и случай, когда расчёт выполнен с неправильной областью или суммой.
4. Расширять пилот по семействам после сверки результатов с ревизором. Сохранять примеры отклонённых форм и проверять новые версии извлечения на ранее принятых комплектах.
