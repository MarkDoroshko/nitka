# Нитка

Локальная сверка отчётов с первичными документами с привязкой результатов к источникам.

Репозиторий предназначен для работы команды на хакатоне.

## Архитектура

- `src/nitka/contracts/` — общие модели входов, извлечения и результатов.
- `src/nitka/extraction/` — чтение документов и ссылки на исходные данные.
- `src/nitka/ocr/` — локальное распознавание сканов.
- `src/nitka/analysis/` — сопоставление и детерминированные правила сверки.
- `frontend/` — пользовательский интерфейс.
- `tests/` — автоматические проверки.
- `examples/` — синтетические примеры.

Входные файлы → извлечение → сопоставление → правила → сохранённый результат. Streamlit вызывает тот же прикладной сценарий, что и библиотечный интерфейс.

## Запуск в Docker

Требуется Docker с Linux-движком на `amd64` (на Windows — Docker Desktop в режиме Linux containers). Сборка скачивает базовый образ и зависимости. Образ фиксирует Python 3.12.16 и версии Python-пакетов с SHA-256 в [requirements-docker.txt](requirements-docker.txt). OCR выполняется на CPU с PaddleOCR 3.7.0, PaddleX 3.7.2 и ONNX Runtime 1.31.1. Для PDF в образе есть кириллические шрифты DejaVu.

1. Подготовьте локальную папку с двумя моделями PP-OCRv5. [Источники и структура папок](config/ocr/README.md) и [контрольные суммы](config/ocr/ppocr-v5.json) приведены в репозитории. При обработке скана приложение сверяет все четыре файла с манифестом.
2. Из корня репозитория соберите образ и создайте том для оригиналов и редакций.

   ```sh
   docker build --platform linux/amd64 --pull --no-cache -t nitka:local .
   docker volume create nitka-runs
   ```

3. Укажите существующую папку моделей в переменной `models`. Пример для PowerShell, если модели лежат в `models/ppocr-v5` в корне проекта:

   ```powershell
   $models = (Resolve-Path -LiteralPath 'models/ppocr-v5').Path
   ```

   В Bash используйте `models="$(realpath models/ppocr-v5)"`. Следующая команда одинакова для обеих оболочек:

   ```sh
   docker run -d --name nitka --publish 127.0.0.1:8501:8501 --mount "type=bind,source=${models},target=/models,readonly" --mount type=volume,source=nitka-runs,target=/data nitka:local
   ```

4. Откройте [интерфейс](http://127.0.0.1:8501). Готовность HTTP можно проверить командой `docker inspect --format '{{.State.Health.Status}}' nitka`. Журнал запуска доступен через `docker logs nitka`.

| Переменная в контейнере | Значение по умолчанию |
| --- | --- |
| `NITKA_OCR_MODELS` | `/models`, папка с каталогами детектора и распознавателя |
| `NITKA_RUNS_DIR` | `/data/runs`, хранилище проверок, редакций и оригиналов |
| `NITKA_CASE_PROFILE` | `/app/config/case5.json`, профиль кейса 5. Для другого профиля смонтируйте JSON только для чтения и передайте путь внутри контейнера через `--env` |

Модели доступны контейнеру только для чтения. Если вес отсутствует или его хеш отличается, сведения об ошибке OCR появятся в диагностике загруженных файлов. Контейнер работает от UID/GID `10001:10001`. Если вместо тома монтируете папку хоста, предоставьте этому пользователю право записи в каталог запусков.

Остановите приложение командой `docker stop nitka`, запустите снова через `docker start nitka`. Чтобы пересоздать контейнер, остановите его, выполните `docker rm nitka` и повторите команду `docker run` с тем же томом `nitka-runs`. Сохранённый запуск можно открыть по его идентификатору.

### Приёмка на документах организатора

Выберите режим «Свои документы». В поле КФЗ загрузите `01_Карточка_учета_фактических_затрат_этап_3.pdf`. В поле первичных документов загрузите файлы с префиксами `02`–`15`, включая файл `10` для проверки дубля. README набора и книга ответов используются при сравнении результатов. Нажмите «Проверить свои файлы».

| Сценарий | Входы | Ожидаемый результат |
| --- | --- | --- |
| Исходный комплект с расхождением | КФЗ и 22 файла первички | 0200, 0300 и 0900 сходятся. По 0800 документы подтверждают 1 133 298,10 ₽ при 1 145 798,10 ₽ в КФЗ. Дельта +12 500,00 ₽ повторяется в итоге по первичным документам. Файл 10 исключён как дубль, 14 относится к другому периоду, 15 — к другому договору. Девять показателей детализации имеют статус «Не проверено». |
| Недостаток подтверждений | Тот же комплект без `02_01_Ведомость_ЗП_Январь_2026.xlsx` | Статья 0200 имеет статус «Не проверено», среди замечаний указан январь 2026 года. Итог по первичным документам также имеет статус «Не проверено». По 0800 сохраняется расхождение +12 500,00 ₽. |

В каждом сценарии откройте доказательства по 0800 и проверьте OCR-фрагмент файла 04. Скопируйте идентификатор запуска, пересоздайте контейнер с тем же томом и откройте сохранённую редакцию. В разделе «Выгрузить редакцию» скачайте JSON и PDF. В JSON проверьте `run_id` и `revision`, в PDF — номер редакции, читаемую кириллицу, суммы, исключения и ограничения проверки. Для прогона без документов организатора в режиме «Демонстрация» доступны [синтетические комплекты](frontend/README.md#три-демонстрационных-комплекта).

## Разработка

Требуется Python 3.12. Из корня репозитория:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m mypy
```

Streamlit принимает КФЗ и первичные документы и показывает итог локальной сверки. Настройка профиля, OCR и хранилища описана в [руководстве интерфейса](frontend/README.md). Синтетические комплекты доступны в режиме «Демонстрация».

Реальные документы, персональные данные, секреты, результаты запусков и веса моделей не входят в этот коммит. Каталоги `data/`, `uploads/`, `runs/` и `models/` исключены из Git; перед добавлением файлов необходимо проверять staged diff.

## Параллельная работа

- `frontend` — Mark: `frontend/` и `tests/test_ui_labels.py`.
- `backend-extraction` — Mark: адаптеры `extraction/`, `ocr/`, конфигурация OCR и их тесты.
- `backend-rules` — напарник: `analysis/`, pipeline, исправления, хранение и их тесты.

Общие контракты, `amounts.py`, `extraction/ports.py`, `extraction/loading.py`, `extraction/normalization.py`, общие фикстуры и корневые настройки меняются последовательно через `main` владельцем Mark с согласованием интерфейсов. Зависимости получают слиянием `main`; одни и те же файлы не переносятся независимо в разные ветки. Роли относятся к переносу и дальнейшей работе, исходное авторство сохраняется.

Проверка общей основы: `python -m pytest tests/test_normalization.py tests/test_validation.py`.

## Проверка и запуск

После установки backend-зависимостей установите `pip install -r frontend/requirements.txt`.
Проверки: `python -m pytest`, `python -m ruff check .`, `python -m mypy`.
Демо запускается командой `python examples/demo.py`, локальный интерфейс — `python -m streamlit run frontend/app.py --server.address 127.0.0.1`.
Настройка локального OCR: [config/ocr/README.md](config/ocr/README.md).

## Границы публичного переноса

Приложение перенесено из снимка `ea9fa187fff605f6a1b1fb9ca4411dce109a52b8` приватного проекта. Учебный договор и связанные тесты адаптированы для публичного примера. Синтетические legacy-фикстуры сохраняют исходные байты для проверки совместимости; это не пользовательские документы.

Не включены реальные документы, персональные данные, секреты, веса моделей, результаты запусков, окружения, кэши, локальные инструкции и навыки агентов, исторические планы и аудиты разработки. Они не нужны для работы приложения либо не предназначены для публикации. Корневая документация и настройки адаптированы для публичного репозитория.

Ветки B04/B05 содержат отдельную дальнейшую разработку, отсутствующую в указанном снимке; в этот перенос она не входит.
