# Фронтенд Нитки

Streamlit-интерфейс демонстрационного контура: выбор комплекта, имитация
обработки, результат сверки, паспорт доказательства, ручная правка с новой
редакцией и выгрузка JSON/PDF.

## Быстрый старт

Из корня репозитория в PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m pip install -r frontend/requirements.txt
.\.venv\Scripts\python.exe -m streamlit run frontend/app.py
```

Интерфейс откроется по адресу `http://localhost:8501`. Запускать команду нужно
из корня репозитория: пакет `nitka` устанавливается в editable-режиме, а адаптер
импортирует реальные правила расчёта из `src/nitka`.

Для PDF нужен TTF-шрифт с кириллицей. Адаптер ищет Arial/Segoe UI в Windows,
DejaVu Sans или Liberation Sans в Linux/macOS. Если ни один шрифт не найден,
JSON продолжает работать, а PDF показывает понятную ошибку.

## Что реализовано

| Область | Файл | Что делает |
| --- | --- | --- |
| Навигация и состояние | `frontend/nitka_ui/application.py`, `app_state.py` | Хранит состояние в `st.session_state`, переключает экраны, вызывает адаптер |
| Экраны | `frontend/nitka_ui/` | Получают данные аргументами и возвращают действие пользователя или `None` |
| Демо-адаптер | `frontend/demo_backend.py` | Загружает комплекты, запускает `analyze_extraction`, хранит редакции, отдаёт источники и экспорт |
| Демо-данные | `frontend/demo_data/*.json` | Три синтетических комплекта в контракте `ExtractionResult` |
| Зависимости | `frontend/requirements.txt` | Streamlit и ReportLab |

`app.py` не содержит правил сверки и не собирает PDF вручную. Это граница
адаптера: позже вместо `DemoAdapter` можно подключить реализацию
`FrontendAdapter` с реальными операциями загрузки, извлечения, сопоставления,
сохранения запусков и экспорта.

Ручная правка использует общий `nitka.corrections.correct_amount`: сохраняет
напечатанный текст и адрес источника, отклоняет неверные суммы и численно
неизменные значения. Демо по-прежнему хранит редакции в памяти сессии. Для
будущего адаптера с дисковым хранением доступны `nitka.storage.correct_run_amount`
и `StoredRun.history`; пример приведён в основном README.

## Три демонстрационных комплекта

| Комплект | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| `clean` | Обе строки отчёта подтверждены актами, суммы совпадают | `NO_DISCREPANCIES`, все проверки `PASS` |
| `discrepancy` | В отчёте аренда `150 000,00`, акт подтверждает `120 000,00` | `DISCREPANCIES_FOUND`, дельта `+30 000,00` |
| `incomplete` | Одна строка подтверждена, вторая неоднозначна, третья без первички; страница акта не распознана | `REVIEW_REQUIRED`, часть проверок `NOT_RUN` |

Комплект `incomplete` специально запрещает зелёный статус: `execution_status`
равен `PARTIAL`, а неподтверждённые суммы не превращаются в ноль.

## Сценарий показа

1. Откройте комплект «Расхождение на 30 000 ₽».
2. Дождитесь имитации обработки и откройте строку «Аренда склада, октябрь».
3. Проверьте паспорт: заявленная сумма, подтверждение, документ, страница,
   исходный текст и расчёт `150 000,00 − 120 000,00 = +30 000,00`.
4. В форме исправления введите `120 000,00` и комментарий.
5. После сохранения создаётся редакция 2: расхождение исчезает, история хранит
   старое и новое значения.
6. На экране экспорта скачайте JSON и PDF. Оба файла относятся к одной паре
   `run_id + revision`.

## Устройство состояния

Состояние хранится одним словарём `nitka_app_state`:

- `screen` — `catalog`, `processing`, `results`, `evidence` или `export`;
- `kit_id` и `snapshot` — выбранный комплекс и текущая редакция;
- `selected_check_id` — открытая проверка;
- `flash` — одноразовое сообщение об операции;
- `artifacts` — кеш JSON/PDF по `run_id + revision`.

Экраны возвращают одно из действий: `OpenKit`, `ProcessingComplete`,
`ViewCheck`, `Navigate`, `SaveCorrection`, `ResetKit`, `ResetAll`.
`AppSession.handle` меняет состояние, после чего контроллер вызывает `st.rerun()`.

## Проверка адаптера отдельно

У `demo_backend.py` есть самостоятельный набор проверок:

```powershell
.\.venv\Scripts\python.exe frontend/demo_backend.py
```

Проверяются:

- загрузка всех трёх комплектов и ожидаемые решения;
- наличие источника и превью у каждой проверки;
- создание редакции 2 после исправления и смена решения на
  `NO_DISCREPANCIES`;
- отказ на нераспознанной сумме;
- сериализация JSON с правильной редакцией;
- генерация PDF с сигнатурой `%PDF-`.

## Экспорт

`DemoAdapter` сохраняет интерфейс для экранов. Каталог JSON-комплектов и кеш
принадлежат `DemoKitRepository` в `nitka_ui/demo_repository.py`; каждый запуск
получает отдельные модели данных. Чистая функция `build_check_views` в
`nitka_ui/check_views.py` собирает представления доказательств для экрана и PDF.

JSON — это `AnalysisResult` текущей редакции в контракте Nitka. Суммы остаются
строками, проверки и источники не пересобираются во фронтенде.

PDF — образец заключения: статус, покрытие, таблица проверок, ошибки обработки
и история редакций. При ошибке PDF JSON всё равно доступен; это соответствует
graceful degradation из плана.

## Ограничения демо

- Данные синтетические, реальные PDF и XLSX пока не загружаются.
- Прогресс обработки имитируется на экране `processing`.
- Исправлять можно только значения уже найденных источников. Подтверждение
  неоднозначного соответствия и ручной ввод отсутствующего источника появятся
  вместе с реальными операциями адаптера.
- Демо хранит редакции в памяти Streamlit-сессии. Постоянное хранение,
  загрузка файлов и настоящая сверка подключаются через `FrontendAdapter`.
